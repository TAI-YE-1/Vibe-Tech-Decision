# 前端框架怎么选

## 默认原则

**已有稳定前端，不因为“框架更现代”而重写。**

框架迁移必须由当前架构无法合理解决的问题驱动，而不是技术偏好。

## 先确认问题

例如：

- 首屏包过大
- 不进入页面也加载页面代码
- 页面生命周期无法释放
- DOM / 事件监听 / 定时器持续堆积
- 状态耦合导致维护困难
- 团队长期维护成本不可接受

这些问题很多可以通过路由拆分、lazy loading、code splitting、模块边界和生命周期治理解决，并不自动意味着要换 React/Vue。

## 什么时候才认真评估换框架

- 当前 UI 复杂度持续增长且现有模式已经形成明显维护瓶颈
- 大量共享状态和组件复用需求难以控制
- 新功能开发持续被当前架构结构性阻塞
- 有足够测试覆盖保护迁移
- 能接受较长时间“双体系并存”或一次性迁移成本

## 证据要求

重大前端迁移至少需要：

1. 当前项目可复现的问题/指标
2. 目标框架官方资料
3. `developer-roadmap` 用于补齐概念地图
4. `realworld` 或同等级成熟实现用于比较真实项目结构
5. 至少一个与目标项目规模/交互复杂度接近的高成熟度开源实现

## 不要这样判断

- React 比 Vanilla JS 高级
- Vue 更简单所以重写
- SPA 就一定性能差
- 一页一路由就一定更快
- 换框架会自动降低 API、DOM 或内存压力

## 输出必须包含

- 保持现状 + 最小修复方案
- 渐进迁移方案
- 全量迁移方案（只有确有必要时）
- 每个方案的收益、风险、验证和回滚方式
