# 前端框架与前端架构

## 这张卡解决什么

当出现“要不要换 React / Vue / Svelte / 其他框架”或“大规模重构前端”的问题时，帮助把**框架选择**和**真实问题**分开。

**这张卡不预设保持现状，也不预设应该换框架。**

## 先理解当前问题

可能相关的维度包括：

- 首屏与路由级加载成本
- code splitting / lazy loading
- DOM 规模与渲染成本
- 页面生命周期和资源释放
- 状态复杂度
- 组件复用
- 可测试性
- 开发速度与维护难度
- 团队/AI 对现有与候选技术的掌握程度
- 生态、插件和长期维护
- SSR / CSR / SSG 等渲染要求
- 可访问性与浏览器兼容
- 迁移期间双体系成本
- 当前测试是否足以保护迁移

## 常见候选

- 保持当前框架/Vanilla 架构并局部治理
- 增加模块化、路由、生命周期、状态边界
- 渐进引入新框架
- 页面/功能级重写
- 全量框架迁移
- 引入更适合特定需求的 meta-framework

没有固定优先级。

## 研究时可参考

- 候选框架官方文档与迁移指南
- `developer-roadmap`
- `realworld`
- 对应生态 Awesome 项目
- `bulletproof-react`（仅 React 架构参考）
- 与目标产品交互复杂度接近的成熟开源项目

## 容易误导判断的说法

- “React 比 Vanilla JS 高级”
- “Vue 更简单所以一定适合”
- “SPA 一定慢”
- “一页一路由一定更快”
- “换框架自然会减少内存/请求”
- “现有代码很多，所以绝对不能迁移”

这些都需要项目事实才能成立。

## 自主判断要求

AI 应区分：

- 当前问题能否通过局部架构变化解决
- 框架迁移能解决哪些结构性问题
- 框架迁移会新增哪些成本

如果证据支持重写，可以建议重写；如果证据支持局部改造，也不应为了“现代化”扩大范围。
