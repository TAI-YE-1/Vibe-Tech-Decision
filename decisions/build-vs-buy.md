# Build vs Buy / Reuse

## 这张卡解决什么

当需求出现时，帮助检查“复用、购买、组合现有能力、自研”这些路径是否都被公平考虑。

**这不是“默认不要自研”的规则。** 自研、开源复用和购买服务都可能是正确答案。

## 建议检查的维度

- 这项能力是否属于产品核心差异
- 当前项目是否已有可复用能力
- 集成边界是否稳定、清晰
- 数据、隐私、合规和部署要求
- 对功能行为的控制程度要求
- 第三方锁定风险
- 供应商/开源项目的维护状态
- 采购与长期使用成本
- 自研开发、测试、运维和升级成本
- 时间要求
- 替换/退出成本

## 常见候选

- 保持现状 / 不做
- 配置或组合当前系统
- 使用现成开源项目
- 使用公共/商业 API
- 使用 SaaS/PaaS
- 自研
- 混合方案

## 可用于发现候选的来源

- `awesome-selfhosted`
- `public-apis`
- `free-for-dev`
- `awesome`
- 当前领域对应的官方生态与高质量项目

见 `sources/source-catalog.yaml`。

这些来源只用于发现候选，最终仍需检查候选本身。

## 常见但不充分的论据

以下说法本身不足以决定方向：

- “自己写更灵活”
- “第三方肯定更稳定”
- “AI 写起来很快”
- “以后可能有很多需求”
- “开源免费”
- “SaaS 省事”

它们都需要结合当前项目的成本和约束。

## AI 应自主判断

如果自研明显更适合，不需要先“证明所有现成方案都失败”。

如果成熟现成方案明显更合适，也不需要为了展示工程能力而自研。

关键是把候选和主要 trade-off 看全。
