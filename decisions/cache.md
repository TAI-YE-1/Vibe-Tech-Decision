# 缓存什么时候该引入

## 默认原则

**先优化源头，再缓存。**

缓存可以隐藏问题，也会引入失效、一致性、容量和故障降级问题。

## 引入缓存前

依次检查：

1. 是否真的慢？
2. 慢在哪里？
3. SQL / 索引 / API / 上游调用能否直接优化？
4. 是否存在重复读取且结果可复用？
5. 可以接受多长时间的数据陈旧？
6. 缓存失效时系统是否还能工作？

## 适合缓存的典型情况

- 高频读取、低频变化
- 计算成本高且结果可复用
- 外部 API 成本高/限流严格
- 热点数据已经有实际测量证据

## 不自动等于 Redis

先判断：

- 单进程内存缓存是否够
- HTTP/CDN 缓存是否更合适
- 数据库自身是否已经足够快
- 多实例之间是否真的需要共享缓存

只有明确需要跨实例共享、TTL、原子操作等能力时，再认真评估 Redis 等独立缓存。

## 输出必须包含

- 当前瓶颈
- 命中率预期
- TTL/失效策略
- 一致性要求
- 缓存不可用时的行为
- 是否值得增加一个独立基础设施组件
