# 缓存

## 这张卡解决什么

帮助判断是否需要缓存、缓存放在哪里、使用什么一致性和失效策略。

**这张卡不要求“必须先优化源头才能缓存”，也不预设 Redis。**

## 建议检查的维度

- 当前性能/成本瓶颈
- 重复计算或重复读取程度
- 数据变化频率
- 可接受的数据陈旧时间
- 命中率预期
- 缓存对象大小
- 单机还是多实例
- 一致性要求
- 失效方式
- stampede / 热点风险
- 缓存不可用时的行为
- 冷启动
- 内存成本
- 运维复杂度
- 安全和多租户隔离

## 常见候选

- 不缓存
- 浏览器缓存
- HTTP / CDN 缓存
- 进程内缓存
- 数据库自身缓存/物化能力
- Redis / Memcached 等共享缓存
- 专用边缘缓存
- 预计算 / materialization

## 两类都可能正确

有些问题应该先优化 SQL、索引或上游。

另一些场景从需求本身就能看出共享缓存、CDN 或预计算是自然设计。

不要强制其中一种路径。

## 研究来源

- 具体缓存产品官方文档
- `system-design-primer`
- `awesome-scalability`
- 与当前负载模式相似的生产案例

## 容易误导判断的说法

- “Redis 很快，所以应该加”
- “缓存会掩盖问题，所以不该加”
- “数据库够快就永远不需要缓存”
- “缓存一定能降低成本”

都需要结合测量和系统语义。

## 自主判断要求

AI 应说明缓存解决的具体问题以及一致性/失效代价；如果缓存是架构本身的一部分，不必人为等待“源头优化失败”后才采用。
