# 实时通信

## 这张卡解决什么

帮助在不同通信方式之间建立完整候选集，并根据当前通信语义自主选择。

**不存在固定的 Polling → SSE → WebSocket 升级顺序。**

## 建议检查的维度

- 单向还是双向
- 客户端到服务端、服务端到客户端各自的消息频率
- 是否需要长期连接
- 并发连接规模
- 消息大小
- 文本还是二进制
- 延迟要求
- 顺序、确认、重试语义
- 断线恢复
- 离线期间消息处理
- 浏览器/客户端支持
- 代理、负载均衡和网络环境
- 服务端资源模型
- 可观测性和调试成本

## 常见候选

- 普通 HTTP 请求
- Polling
- Long Polling
- SSE
- WebSocket
- Webhook（系统到系统）
- 消息队列/事件流（后端内部）
- WebTransport 或其他更具体协议（当场景需要时）

这些候选解决的问题不同，不是成熟度等级。

## 研究来源

- 浏览器、协议、框架官方资料
- `system-design-101`
- `system-design-primer`
- 与当前连接规模和语义相似的成熟实现

## 常见启发式

例如：

- SSE 经常适合服务端到浏览器的持续文本事件
- WebSocket 经常适合长期双向交互
- Polling 在低频、简单场景可能成本最低

这些只是常见模式，**不是规则**。代理限制、连接规模、既有基础设施或产品语义都可能改变答案。

## 自主判断要求

选择协议时说明关键通信语义和限制即可；不要为了遵循某种“最简单优先”原则而忽略更适合的方案。
